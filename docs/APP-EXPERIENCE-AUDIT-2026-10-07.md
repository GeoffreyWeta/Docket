# DOCKET app experience audit

Audit date: 7 October 2026 (Africa/Lagos). Local workspace build; this is not a test of the hosted production deployment.

Implementation update: the interaction fixes below have now been implemented in the shared application/demo code. The original findings are retained as the audit record. See `UX-FIXES-2026-10-07.md` for the changes, checks, and remaining work. The hosted demo has not been deployed from this session.

The core procurement controls held up well in the automated workflow tests. The main obstacles to excellent everyday use are account isolation in the browser, losing unfinished work, misleading recovery feedback, deadline handling, mobile form overflow, accessibility, and the amount of data loaded for each visit and action.

This report separates reproduced browser defects, code-confirmed risks, and suggested product improvements. Priority is based on user impact, not how easy a change is to implement. P1 means address before relying on the affected workflow; P2 means address in the next usability/reliability release; P3 means a planned improvement. No changes to application behavior were made.

## Coverage and evidence

- Headless Chromium: all 12 original demo accounts, plus two vendor accounts created by the workflow test. These cover executive, senior/mid/junior procurement, approver, evaluator, auditor, and supplier perspectives.
- Public entry screens: landing, sign-in, vendor registration, password recovery, and setup entry.
- Desktop role pages and role home screens at 390px and 768px. Additional focused mobile checks of new tender, tenders, suppliers, finance, analytics, and team.
- Tender detail pages and vendor, bid, evaluation, and round tabs across published, evaluation, approval, and awarded examples.
- Targeted browser exercises: unsaved tender reload, offline password recovery, supplier switching with a saved bid draft, nested list actions, RFI selection, and dark analytics.
- Automated accessibility scans using axe. Some broad scans captured the loading skeleton while a page was changing; those transient results are not treated as defects in the destination page.
- Production frontend build passed. Django system check passed.
- Procurement lifecycle: **217 checks passed**. Auctions: **96 passed, 0 failed**. Roles: **27 passed, 0 failed**. Approval/setup: **57 passed, 0 failed**.
- Smoke script printed success for all its assertion groups, including authentication, platform, two-stage opening, reminder mail, permissions/import/templates/compliance, MFA/sessions, and renaming. Its redirected Windows run also produced console-email Unicode encoding errors; it was not a clean test run.
- No uncaught JavaScript errors were recorded during the broad role-page run. This does not prove every interaction is error-free.

Local evidence is under `../.audit/`: `browser-results.json`, `journeys.json`, `edges.json`, `final-probes.json`, screenshots, and backend test logs. The original `backend/db.sqlite3` was not used for mutations. Workflow and browser changes occurred in an isolated audit database; other suites used a separate copied test database.

The standalone administration console was reviewed through code and permission tests, not a full browser session. Real email delivery, external finance synchronization, AI responses, hosted deployment performance, real screen-reader use, Safari/Firefox, and physical devices were not validated. This is a broad audit, not a claim that every possible user action or production condition was tested.

## Highest-priority defects and risks

| ID | Priority / evidence | What hinders use | Update needed |
| --- | --- | --- | --- |
| 1 | P1 / browser reproduced | **A supplier can inherit another supplier's unsubmitted bid prices on a shared browser.** The local draft key contains only tender and round. In an isolated test, Coldline's stored unit rate `9876` appeared in Harmattan's bid room after switching accounts. This concerns local draft data; it is not evidence that the API exposed a sealed bid. | Include workspace/backend, supplier identity, tender, and round in draft keys. Migrate or remove old unscoped drafts. Define a shared-device clearing policy. |
| 2 | P1 / browser reproduced | **Refreshing a new tender loses unfinished input.** Typing a title and reloading returned an empty field. Buyers drafting a long scope or many lines face avoidable rework. A manual Save as draft action exists, but there is no automatic recovery in this form. | Save a scoped recoverable draft, show save status, and warn before navigation discards unsaved edits. Test reload, browser Back, internal navigation, and session expiry. |
| 3 | P1 / browser reproduced | **Password recovery claims success while offline.** Clicking Send reset link without a connection showed “a reset link is on its way.” The handler catches every failure and sets the success state. | Preserve the same account-neutral response for valid server responses, but distinguish network/server failures and offer retry. Add submission state to prevent repeat clicks. |
| 4 | P1 / code confirmed | **The same selected deadline means different instants for users in different time zones.** NewTender constructs `date + T17:00:00` in the operator's browser zone, while the workspace has a configurable time zone. Editing a draft also converts an existing timestamp to a UTC date and saves it as browser-local 17:00. | Pick an explicit closing time in the workspace zone, convert consistently on the server, show the zone, and preserve an existing timestamp when unrelated fields are edited. |
| 5 | P1 / code confirmed | **Real and demo sessions share the same localStorage token keys, while the backend selection is tab-specific sessionStorage.** A sign-in in another tab can overwrite the token used by a real-workspace tab. No storage-event reconciliation is present in App. | Scope tokens and identity to the backend/workspace and synchronize session changes across tabs. Test simultaneous real/demo tabs and two accounts. A separate production/demo deployment is necessary but does not alone fix the browser-key collision. |
| 6 | P1 for non-NGN workspaces / code confirmed | **Currency configuration is broader than currency handling.** `fmtMoney` defaults to NGN, `fmtCompact` hardcodes naira, supplier instructions explicitly request naira, and many callers do not supply the configured currency. Finance FX logic also treats NGN as the base currency. | Either make NGN the clearly supported fixed base currency and restrict setup accordingly, or propagate and enforce the workspace base currency through forms, calculations, FX exclusions, charts, and exports. |
| 7 | P2 / browser reproduced | **The new-tender form overflows a phone.** At 390px, document width reached 497px. The FrostLine vendor chip's long “unverified / no email” metadata caused the overflow. Main lists fitting the screen does not mean the creation journey does. | Let chip metadata wrap; constrain chip width and use `min-width: 0` appropriately. Verify long company names, metadata, and translated text at narrow widths. |
| 8 | P2 / browser and code confirmed | **RFI promises an information-only process but shows mandatory pricing and commercial scoring.** Selecting RFI still showed maximum unit prices, price-based scoring, and a checklist requiring priced lines. The screen says “No award, no prices compared.” Backend handling does not visibly branch into a separate RFI lifecycle. | Define an information-only RFI flow: questionnaire/documents, no compulsory prices, and an explicit close/shortlist outcome. Ensure the server enforces the same distinction, or remove the misleading promise until supported. |
| 9 | P2 / browser scan and code confirmed | **Clickable list rows contain interactive buttons.** Procurement tender/supplier lists and evaluator queues triggered nested-interactive findings. The shared Row component handles Enter on the parent without checking the event target and does not implement Space activation. | Use a real link for the record title with sibling action buttons. Ensure a child action never triggers parent navigation and that keyboard behavior matches native controls. |
| 10 | P2 / browser scan and code confirmed | **Tab semantics are incomplete or invalid.** Tender tablists include a non-tab compliance action; tabs are missing a complete panel association and expected keyboard navigation. | Keep toolbar actions outside the tablist; implement tab IDs, associated tabpanels, roving tab focus, and arrow/Home/End keys, or use ordinary navigation links. |
| 11 | P2 / browser scan | **Some text and headline numbers have insufficient contrast.** The landing preview had 10 failing nodes in the desktop scan. Amber finance/analytics figures reached only 2.16:1 against white; large text requires 3:1 for this check. Additional muted labels also failed. | Adjust shared color tokens and chart/stat tones, then validate light/dark themes and configured accents. Dark analytics did not show a contrast failure in the targeted scan; the problems are not universal. |
| 12 | P2 / browser scan | **Password recovery has an unnamed input; public screens lack useful landmarks/headings.** The email label is visually present but not programmatically associated. Public sign-in/register/recovery screens lack a main landmark and first-level heading. Several app cards skip heading levels; some tender tables have empty headers. | Associate all labels and inputs, add main/h1 landmarks, use a coherent heading hierarchy, and name action-column headers. |

## Reliability, performance, and administration

| ID | Priority / evidence | Finding | Update needed |
| --- | --- | --- | --- |
| 13 | P2 / build measured | **Every entry loads a large app bundle:** 1,117.24 KB minified JavaScript, 322.28 KB gzip, with a Vite size warning. App statically imports most screens. First-time suppliers also pay for buyer/finance features. | Split public, supplier, buyer, finance, and administration screens with lazy imports. Measure first usable interaction on a throttled mobile connection and a cold cache. |
| 14 | P2 / code confirmed | **Bootstrap loads the full visible portfolio and vendor register.** App refetches on navigation, after actions, and periodically. Supplier lists have client-side “show more,” but that does not reduce the server response. | Add paginated/searchable endpoints and fetch details on demand. Refresh changed entities instead of repeatedly rebuilding the whole workspace. Benchmark against the real 1,400-vendor register and large tender/audit histories. The browser test used the smaller seeded register. |
| 15 | P2 / code confirmed | **Requests can wait indefinitely from the client's perspective.** The shared fetch wrapper has no AbortController timeout or cancellation. Background failures preserve existing data without a persistent freshness indicator. | Add sensible timeout/cancel behavior, show connection and last-refresh status, and retry safe reads. Do not blindly retry writes such as bids or invitations; use idempotency/reconciliation first. |
| 16 | P2 / code confirmed | **Notification emails are sent serially during business actions.** Graph calls can wait 30 seconds and retry. Large vendor notices can make an action feel stuck even though its business record has already changed. Failures are logged rather than presented as a delivery queue. | Use an outbox and background sender with per-message delivery state, retry policy, and administrator visibility. Keep the business action independent of email latency. This is an architectural risk, not a measured live-mail outage. |
| 17 | P2 / code confirmed | **TOTP has no visible self-service lost-device recovery path.** Turning it off requires a current authenticator code; no backup-code flow was found in the reviewed UI/authentication code. | Provide single-use recovery codes and a carefully audited administrator recovery process. Explain and confirm recovery readiness during enrollment. |
| 18 | P2 / code confirmed | **No React error boundary was found.** Network failures have messages, but a component render failure has no equivalent in-app recovery surface. | Add boundaries around major screens with retry/reload, a safe navigation option, and useful error reporting. Do not discard local drafts when recovering. |
| 19 | P2 / code confirmed | **Press-and-hold confirmation depends on raw pointer/keyboard events.** HoldButton has no click activation handler. Screen readers, voice control, or switch tools that synthesize a click may be unable to confirm. | Offer an accessible explicit confirmation alternative. Keep keyboard hold if useful, but test real assistive technologies; this impact was not validated with a screen reader. |
| 20 | P3 / local run reproduced | **Console email logging can fail on Windows when a message includes naira.** The redirected smoke run logged UnicodeEncodeError even while its assertions reached success markers. | Set UTF-8 for local/test output or use an in-memory email backend for tests. Separate test failures from logging failures in the runner. |

Production-readiness items acknowledged by the repository also need a decision before expanding adoption: upload malware scanning, SSO where required, signature-provider/legal-template requirements, data-volume pagination, and the deliberate single-tenant deployment model. These are requirements/limitations, not newly reproduced browser defects. Dependency currency and known-vulnerability status were not checked online in this audit.

## Improvements by user perspective

These are recommended design updates, not claims that each feature is currently absent.

| Perspective | What excellent use should feel like | Recommended next improvement |
| --- | --- | --- |
| First-time visitor | Understand the product, their route in, and how to get help quickly. | Make buyer versus supplier entry explicit; state whether the current page is a demo or a real workspace. Provide a clear help/contact route. |
| New employee / vendor | Complete onboarding without guessing who owns the next step. | Explain access codes, invitation expiry, registered versus verified status, and how to request a replacement invitation. Validate early and retain entered details after recoverable errors. |
| Supplier | Prepare a bid confidently on a phone or unreliable connection. | Fix identity-scoped draft recovery first. Provide a clear submission receipt with timestamp, round, files, acknowledged addenda, and replacement/withdrawal rules. Add upload progress, cancellation, and retry feedback for slow connections. |
| Procurement officer | Draft a substantial event without losing work. | Add saved/recovered draft status, workspace-zone closing time, and an RFI-specific flow. Keep advanced controls out of the basic route, and test long line-item forms on mobile. |
| Procurement manager / head | See blockers and intervene without navigating through every event. | Surface owner, current blocker, next deadline, and required action together. Show communication delivery status after vendor notices. |
| Evaluator | Know what can be scored and finish without navigation surprises. | Resolve nested controls and tab semantics. Make COI state, submitted versus unfinished scores, and required written justification unmistakable. Add keyboard-first and assistive-technology journey testing. |
| Approver / department head | Understand the decision and authority required at a glance. | Put amount, basis, recommendation, exceptions, prior signatures, and the effect of approve/return together. Make the next signer and escalation route obvious. |
| Executive | Read trustworthy figures without learning the whole operating workflow. | Use high-contrast measures, explicit calculation basis, data freshness, and drill-through to supporting records. Preserve the separation of different savings measures. |
| Finance user | Trust the ledger and distinguish missing data from withheld data. | Align reporting currency with calculations. Keep feed age and permission-limited data prominent. Test import/reconciliation failures and recovery with real connectors in staging. |
| Auditor | Trace a decision and retrieve evidence without hunting. | Preserve hash verification and exports; improve accessible tables and the path from a decision to COI, opening, scores, signatures, and communications. |
| Administrator / support | Diagnose a blocked user without silently changing procurement history. | Add operational views for failed email, integrations, job health, stale data, and account recovery. Test the standalone console in the browser before claiming complete admin coverage. |
| Shared-device / multi-tab user | Keep company/account context consistent. | Fix token and draft namespace isolation, account-change synchronization, and an explicit shared-device sign-out policy. |
| Keyboard / low-vision / assistive-tech user | Complete the same meaningful tasks independently. | Fix labels, contrast, nested controls, tabs, and hold confirmation. Supplement automated scans with actual screen-reader and voice/switch-control testing. |

## Recommended release order

1. **Protect identity and unfinished work:** findings 1–5. Add meaningful regression checks for switching supplier accounts, real/demo tabs, offline recovery, unsaved navigation, and deadline preservation.
2. **Make forms consistent and usable:** currency support decision, mobile chip wrapping, information-only RFI behavior, labels, tab/list semantics, and contrast. Validate the actual end-to-end mobile bid and approval journeys.
3. **Improve smoothness under load:** route splitting, paginated APIs, incremental refresh, timeout/freshness feedback, and asynchronous email delivery with operational status.
4. **Complete production and inclusive-use validation:** MFA recovery, render recovery, accessible confirmation, hosted staging tests, real connectors/mail, physical phones, additional browsers, screen readers, and the standalone admin console.

Keep the existing strong controls: role-aware landing, sealed-data enforcement, conflict-of-interest gates, recorded envelope opening, approval separation, audit integrity, recoverable supplier drafts once correctly scoped, readable error messages, and finance freshness/basis explanations. The passing workflow tests give a useful foundation; they should be complemented by repeatable browser journeys rather than treated as proof of excellent UX.

## Focused interaction UX follow-up

This pass specifically examined refreshing while typing, cursor selection, numeric entry, scrolling, tab persistence, and text wrapping. Evidence: `.audit/ux-detail.json`, `.audit/ux-inputs.json`, and `.audit/ux-navigation.json`.

### Reproduced interaction problems

1. **Silent changes to an entered bid amount - P1.** In the existing lump-sum field, pasting `1250.75` becomes `125075`, displayed as ₦125,075. Pasting `-1250` becomes positive `1250`. This was tested using a line-free browser fixture to exercise the existing lump-sum UI; no such bid was submitted. Stripping invalid characters can change the user's commercial intent. Either support decimals consistently or reject them with an explicit explanation. Reject negative amounts instead of silently changing their sign.
2. **Navigation opens the next page halfway down - P2.** After scrolling the desktop new-tender pane to 650px and clicking Tenders in the sidebar, the next page retained a 650px pane scroll position. The route-change effect scrolls `window`, while the Studio layout actually scrolls `.main`. Scroll the active pane to the top on a new destination; separately restore the previous position when the user goes Back.
3. **Background refresh does not refresh Finance - P2.** While Finance was open, a wake refresh made one bootstrap request and zero finance requests. Finance's own load effect depends on the year and local reload counter, not the global polling update. Consequently another person's ledger changes may not reach this screen. Give Finance its own freshness/revalidation policy and update indicator; preserve its selected filters and tab.
4. **A full refresh forgets the selected Finance tab - P2.** Clicking Spend left the URL at `/app/finance`. Reloading returned to Savings. Store tab/year/dimension selections in the route and restore them on reload and Back. Supplier portal tab selection and several list filters also live locally in the reviewed code and need the same persistence review.
5. **Long vendor metadata forces horizontal scrolling - P2.** A 390px new-tender viewport became 497px wide. The offending chip was 466px wide because its company/status metadata inherited `white-space: nowrap`. Wrap metadata normally and constrain the chip to the available width. Use one-line ellipsis selectively for identifiers, with a way to inspect the full value; do not truncate important errors or instructions.
6. **Unfinished tender text disappears on a full reload - P1.** This is the previously reproduced draft-loss issue. Make “saved,” “saving,” “unsaved,” and “recovered” visible states; preserve work through reload and interrupted sessions.

### What the refresh tests actually showed

- The ordinary 30-second background bootstrap update preserved the new-tender input's value, the same DOM node, keyboard focus, and selection range `7–13`.
- A real focus-triggered bootstrap refresh preserved a supplier unit-rate input's value, DOM node, focus, and selection range `1–3`.
- These observations do not establish that every form is safe under a changed deadline, new round, changed permissions, removed record, or session expiry. They do establish that routine refresh does not automatically clear the tested fields. A background data refresh and a browser reload have different effects here.
- Mobile title input measured 16px text and 46px height. The tested basic field is appropriately sized; a blanket claim that every input is too small would be incorrect.

### Further interaction improvements supported by code review

| Area | Current concern | Recommended behavior |
| --- | --- | --- |
| Typing cost | Supplier draft storage writes the entire price draft synchronously to localStorage on each value change; form-level state also recalculates totals/checklists and renders many fields. Slow typing was not measured on a low-end device. | Debounce storage and flush on blur/page hide; isolate field renders and profile 40–100-line forms on a throttled device. Keep visible totals responsive. |
| Evaluation save feedback | Scores save per action; written notes save on blur. There is no clearly dedicated per-note saved/saving/failed indicator. | Display save state next to the note and make failed changes visibly pending with retry. Preserve notes on navigation/session interruption. |
| Rapid score changes | Consecutive score writes can overlap; a quiet refresh follows the latest tracked promise. This was reviewed, not reproduced as data loss. | Serialize or version writes per bid/criterion, reconcile the accepted server value, and test delayed/out-of-order responses. |
| Moving checklists | Completing a field reorders and animates checklist items. This is intentional, but can move the target someone was about to select. | Keep checklist order stable during active interaction, or clearly separate remaining/completed items. Validate with keyboard and reduced-motion users. |
| Text and totals | Some row text wraps, while money/line totals use nowrap or ellipsis. Important values can become difficult to inspect in a narrow column. | Show complete actionable amounts; wrap descriptions at sensible boundaries, handle long unbroken strings, and test long filenames/company names and 200% zoom. |
| Loading/errors | Finance's error branch replaces the page with an error card; the reviewed branch has no local retry button. Other background errors keep old data without always showing a freshness state. | Retain the last usable view, state when it was updated, and offer retry. Use a skeleton for first load, not to blank an already usable screen. |
| Round changes during bidding | Draft identity depends on the active round, but BidRoom remains keyed by tender and its initial draft state is only read once. A round change needs careful reconciliation; this transition was not browser-tested. | Tell the supplier the round changed, preserve the old draft under its original identity, and deliberately initialize a separate new-round draft. |

The interaction UX release should begin with numeric-entry safety, draft protection, correct pane scrolling, view-state persistence, and mobile wrapping. Then address typing cost, save-state feedback, and refresh consistency. Treat refresh as a data update that preserves the user's editing context, with an explicit notice when changed business state requires intervention.
